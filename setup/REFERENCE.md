# Dotfiles deployment reference

Read only the sections relevant to the current task, as directed by CLAUDE.md.
These details are preserved from the former startup instructions.

## Layout

| Path                  | Contents                                                        |
| --------------------- | --------------------------------------------------------------- |
| `.zshrc` / `.zprofile` / `.zshenv` | Shell entry points, symlinked to `$HOME`           |
| `zsh/`                | `aliases.zsh`, `functions.zsh`, `zinit.zsh`, `extra/` snippets    |
| `zsh/os/`             | macOS-only shell config: `macos-{env,interactive}.zsh`             |
| `zsh/abbreviations`   | zsh-abbr's store, read via `$ABBR_USER_ABBREVIATIONS_FILE`        |
| `.config/`            | Every entry is symlinked to `~/.config/<name>`                    |
| `.config/git/`        | `ignore` (global excludes) and `allowed_signers` (SSH signing)     |
| `homebrew/Brewfile`   | The package set                                                   |
| `setup/lib.sh`        | The longer installer sections, sourced by `install.sh`            |
| `setup/`              | Opt-in scripts (`SETUP_SCRIPTS="pnpm composer" ./install.sh`)      |
| `themes/voltage.md`   | Canonical palette + the list of files that carry it               |
| `iterm/`, `obsidian/` | App-specific config                                            |
| `.claude/CLAUDE.md`   | Global Claude Code instructions                                   |
| `.claude/REFERENCE.md` | The reasoning behind them, read on demand rather than every session |
| `.claude/hooks/`      | `notify.sh`, the Notification hook (terminal-notifier); `search-excludes.sh`, the PreToolUse hook that rejects a widened rg/fd missing the noise-folder excludes; `resume-after-limit.sh`, the StopFailure hook (and launchd sweep) that resumes a session once the usage limit resets |
| `.claude/statusline.sh` | The status line — plan usage, context, model, on every render   |
| `.claude/skills/`     | Skills, one dir per skill — ten vendored, `backfill-protocol` ours |
| `.claude/agents/`     | Custom subagents, one `.md` file per agent, ours                  |
| `.claude/commands/`   | Custom slash commands, one `.md` file per command, ours           |
| `.claude/rules/`      | User-level rules loaded in every project, one `.md` file per ruleset; `token-efficient` vendored, `human-writing` and `code-style` ours |
| `launchd/`            | macOS LaunchAgent plists, loaded by `install.sh` (not symlink-only); the hosts-refresh LaunchDaemon is generated by `install.sh` instead, named after the installing user |

### Leftovers on older installs

`~/Library/Fonts/HackNerdFontColor-Regular.ttf` may sit on a machine that
installed the old Ghostty tab-icon font. Nothing reads it; delete it by hand.

### Git configuration

The two `.config/git/` files reach git by different routes, which matters when
one of them appears not to work: `allowed_signers` is named explicitly by
`.gitconfig`'s `allowedSignersFile`, while `ignore` has no `core.excludesFile`
pointing at it at all — git reads `$XDG_CONFIG_HOME/git/ignore` on its own, so
the symlink is the whole wiring.

GitButler doesn't read `commit.gpgsign`. It signs according to
`gitbutler.signCommits` and then uses the same `gpg.format`, `gpg.ssh.program`
and `user.signingkey` as git. `.gitconfig` sets it to `true` globally, but a
repo-local value wins over the global one, and a stray repo-local `false` (cause
unknown) has sent commits out unsigned before. If a repo's commits show up unverified on GitHub, run
`git config --show-origin --get gitbutler.signCommits` there before blaming
1Password or the key.

### Agent deployment and vendored skills

`.claude/` is tracked in full but only partly deployed: `install.sh` links
`CLAUDE.md`, `REFERENCE.md`, `hooks/notify.sh`, `hooks/search-excludes.sh`, `hooks/resume-after-limit.sh`, `statusline.sh`, every file under `agents/`,
every file under `commands/`, every file under `rules/` and every directory
under `skills/`, so
`themes/my-theme.json` rides along for reference and is applied by hand. The
installer also sweeps the retired `~/.claude/AGENTS.md` link on re-run.

`skills/` is a loop over `skills/*`, not one `link` line per skill, for the same
reason `.config/*` is — a skill added here but not named in the installer would
silently never deploy, the exact failure mode that killed the `@AGENTS.md`
import. The loop links every directory unconditionally, since a plain skill is
discovered by its *directory* containing a `SKILL.md`, while a directory that
also carries a `.claude-plugin/plugin.json` is discovered a second way — as a
full Claude Code plugin, auto-loading as `<name>@skills-dir` — and doesn't need
a `SKILL.md` of its own at all if its manifest points at `commands/` instead.
The sweep alongside the loop removes only links that point into this repo, so
a skill installed by hand from elsewhere survives.

`agents/` is the same loop-not-list pattern, one level shallower: a subagent is
discovered by a `.md` file directly under `~/.claude/agents`, so the file itself
is what gets linked, not a containing directory. Each file's frontmatter sets
its own `model` — `quick-lookup` (haiku), `researcher`/`code-reviewer`/
`feature-scout`/`heavy-refactor` (sonnet) for search, review, survey and
structural work, and `bug-hunter` (opus, `effort: high`) for tracing a defect
or a missing error path across callers and callees. `heavy-refactor` is on
sonnet because on opus a 7-day token audit put it at 26% of all usage, ~60M
tokens per run; `bug-hunter` at `xhigh` was another 23%. One pass on sonnet
is still cheaper than two, and a refactor that needs opus can ask for it.
`CLAUDE_CODE_SUBAGENT_MODEL=sonnet` in `.zshenv` is only the fallback for
subagents with no `model:` of their own — the built-ins (Explore,
general-purpose, Plan) — not for these. `researcher`, `code-reviewer`,
`feature-scout`, and `bug-hunter` also carry `memory: project`, so findings
persist per-repo across runs; `heavy-refactor` and `quick-lookup` don't —
`quick-lookup` answers are too narrow to be worth retaining and
`heavy-refactor` runs are one-off enough that stale memory would be more
likely to mislead the next run than help it.

`commands/` follows the identical loop-not-list pattern one level shallower
still: a slash command is discovered the same way a subagent is, by a `.md`
file directly under `~/.claude/commands`. `hunt-bugs.md` and
`scout-features.md` are manual shortcuts for `bug-hunter` and `feature-scout`
— each sets `disable-model-invocation: true`, so Claude doesn't also
auto-fire the command on top of the agent's own `description`, and
its body just tells Claude to invoke the Agent tool with that `subagent_type`
directly. The frontmatter mechanism Claude Code's own docs describe for this
— `context: fork` plus `agent: <name>` — reads as the more direct way to
write it, but is a confirmed live bug for any agent outside the three
built-ins (`Explore`, `Plan`, `general-purpose`): the command's body runs
inline in the main context instead of forking into the named subagent
(anthropics/claude-code issues #21725, #20604). Don't switch these two files
to that frontmatter until that's fixed upstream.

`skills/backfill-protocol/` is the one repo-owned skill. It isn't a section of
the root `CLAUDE.md` because no job in this repo touches data, so ~600 tokens
would load into every dotfiles session for a protocol that only matters in a
project with a database. As a skill it costs one listing line everywhere and
loads in full when a job starts. The root file keeps a two-line pointer so the
"snapshot first" rule still fires before a job begins. Edit it in place; it has
no upstream.

The other ten skill directories are **vendored, not ours**.
`skills/plain/` comes from `petekp/claude-code-setup`
(`skills/plain/SKILL.md`); `skills/javascript-pro/`, `skills/swift-expert/`,
`skills/php-pro/`, `skills/vue-expert-js/`, `skills/vue-expert/`,
`skills/database-optimizer/`, `skills/nextjs-developer/`,
`skills/react-expert/` and `skills/react-native-expert/` come from
`Jeffallan/claude-skills` (MIT), each with its `references/` directory,
because the SKILL.md's "Reference Guide" table is five dead links without
them — `vue-expert-js` additionally defers to three files under
`../vue-expert/references/` for concepts it shares with the TypeScript
version, so the two are vendored together or not at all. They are upstream's
files. Re-fetch with `gh api` and diff rather than editing in place; local
edits would be silently lost the next time one is refreshed:

```sh
gh api repos/Jeffallan/claude-skills/contents/skills/swift-expert/SKILL.md \
  -H 'Accept: application/vnd.github.raw'
```

`rules/token-efficient.md` is the root `CLAUDE.md` of
`drona23/claude-token-efficient` (MIT), unedited. The same refresh-and-diff rule
applies; `.claude/REFERENCE.md` (under *Context and settings maintenance*) has
the command and what was left out of upstream.

`rules/human-writing.md` is ours: write anything a person
reads the way you'd say it out loud, and cut the tells of machine-written
text. It expands the *Write like a person* bullet in `.claude/CLAUDE.md`
rather than replacing it, because Codex reads that file and never reads
`~/.claude/rules/`, so the bullet is all Codex gets. It is a rule and not a
skill because it has to apply to every reply and commit message, and a skill
only loads when something triggers it. That also means it loads into every
session, so keep it short: it is about 2.7k characters (~680 tokens est.),
and `AGENTS.md` doesn't repeat its word and phrase list.
`blader/humanizer` (MIT, ~60k stars) was the obvious thing
to vendor instead and was passed over. It's a skill for rewriting text after
it's written, not standing guidance, and far too long to load every session.
If rewriting pasted text ever becomes a regular job, vendor it as a skill
next to this rule rather than growing the rule. Edit this file in place; it
has no upstream.

`rules/code-style.md` is ours: the code rules condensed from the *Clean Code*
and *Code Complete* rule sets. Claude Code loads it like the other rules. Codex gets it
through a pointer in the *Code style* section of `.claude/CLAUDE.md` and reads
it on demand, which keeps one copy instead of pasting it into `CLAUDE.md`,
where it would be paid for twice in Claude sessions. It carries `paths:`
frontmatter listing source-file extensions, so it loads only once a session
works with a matching file. A new language needs its extension added there.

Its *Written by hand* section comes from neither book. It lists what gives
generated code away (guards for impossible states, single-caller helpers,
template-shaped functions, leftovers) so a diff reads like the file's owner
typed it. It sits in this rule and not in a file of its own because a second
file would have to repeat the `paths:` list and get its own Codex pointer in
`.claude/CLAUDE.md`. The comment and docblock tells stay under *Comments*.

The two full rule sets are about 29k characters (~7.2k tokens est.) and repeat
each other on comments, errors, class design, tests and the review checklist.
Path scoping doesn't save much, because the lists include `*.sh` and
`*.zsh` and nearly every dotfiles session touches one. The condensed rule is
about 8.8k characters (~2.2k tokens est.) with its docblock and hand-written
guidance. The full
text of both sits, verbatim apart from heading levels, in **Code rules in full** at the end of
`.claude/REFERENCE.md`, read only for refactors, reviews, concurrency work or
when the short rule is unclear. Putting it in the *Code style* section instead
was ruled out: `.claude/CLAUDE.md` says to read that section before writing
any code, which would pull the whole 29k back in through a Read. The rule says
a project's own `CLAUDE.md` or `AGENTS.md` wins and limits cleanup to the code
a task changes, so it doesn't contradict *Scope to the request*. Edit it in
place; it has no upstream.

Vendoring verbatim means four of them contradict the style rules in
`.claude/CLAUDE.md`. That is deliberate: correcting it in the file would be
thrown away by the next refresh, so it is recorded here instead. The global
rules win — these skills are reference material, not authority.

- `javascript-pro` writes every example with double quotes and semicolons, the
  opposite of the JS rule (single quotes, no semicolons, 80 cols, via
  `~/.prettierrc`). It states no quote rule anywhere, so this is
  conflict-by-example only — follow Prettier and ignore the examples'
  punctuation. Its workflow also mandates `eslint --fix` and Jest at 85%
  coverage; `eslint` and `prettier` are installed as pnpm globals but **`jest`
  is not installed at all**, so that step only applies when the repo being
  worked on ships it.
- `swift-expert` ends its workflow at `swift build` / `swift test`, which is not
  how Swift work finishes here — the global rule is `./build.sh --install`, and
  one of the projects uses a different build tool entirely. It also assumes
  SwiftUI and Swift 5.9+, while the projects here are AppKit at tools-version
  6.0. Take its concurrency, actor and protocol guidance; not its build steps.
- `php-pro` writes every example with single-quoted strings and a trailing
  comma after the last constructor-promoted property, the opposite of the PHP
  rule (double quotes, no trailing commas, PHP 8.1 target) — it targets PHP
  8.3+. Follow the repo's PHP rule and ignore the examples' punctuation and
  version. Its verify step also mandates `phpstan analyse --level=9` and
  `pest`/80%+ coverage; only `php-cs-fixer` is installed here, so PHPStan and
  Pest apply only when the repo being worked on already has them in
  `composer.json`.
- `react-expert` writes every example with semicolons, the opposite of the JS/TS
  rule (no semicolons, via `~/.prettierrc`) — its quote style (single) does
  match. Follow Prettier and ignore the examples' semicolons.
  `react-native-expert` and `nextjs-developer` don't have this problem; their
  examples are already semicolon-free.

### Claude settings, hooks and usage refresh

`~/.claude/settings.json` is **not** tracked: it is mostly state Claude writes
itself (model, `enabledPlugins`, the atuin hooks), so a symlink would fight it.
The blocks that wire the deployed scripts live in
`.claude/settings.portable.json` instead, and `merge_claude_settings()` merges
them in: three `Notification`, `PreToolUse` and `StopFailure` hook groups and
the top-level `statusLine`.

Hooks merge differently from every other key. Each event already holds entries
other tools wrote (atuin, nodeterm), so replacing `hooks` the way a top-level
key is replaced would delete them. The merge only appends, and skips a portable
hook whose `command` is already anywhere under its event, so a block pasted
into `settings.json` by hand isn't doubled. The cost is that
removing a hook from the portable file doesn't remove it from a machine; delete
it from `settings.json` by hand. `setup/check-claude-settings.sh` tests the
merge against a temp config.

`search-excludes.sh` is the backstop for the search-folder rule in
`.claude/CLAUDE.md`; `.claude/REFERENCE.md` says what it checks and what it
misses. `command-guard.sh` is the backstop for every "never run" rule in the
global and repo instructions; its header lists them, why `permissions.deny`
wasn't used, how it follows indirection through `shfmt`'s syntax tree and the
newest shell snapshot, and the forms it still misses. It costs about 50 to 85 ms
a call, mostly one `shfmt` and one `jq` process per source
it parses, against about 28 ms for the earlier awk splitter.
`resume-after-limit.sh` marks a session that died on the usage limit; the
usage-refresh LaunchAgent then runs the same
script with `--sweep` after each refresh and resumes the session headless once
the cache shows the limit has reset. The script's header covers when it holds
back and why the resume goes through a login shell.

`Notification` is the only event that banners, on purpose — it fires when Claude is
blocked on you (a permission prompt, an idle question). `Stop` would banner
every turn, which is how you end up leaving Do Not Disturb on.

The status line is where the plan's usage windows live, because `/usage` only
answers when asked and the 5-hour window is usually already the reason you
asked. Four rows — session, week, Fable week, context — each a bar plus a
countdown, using Claude Code's own names for the windows so the two never
disagree. The Fable row is the odd one: Claude Code tracks that window and draws
it in `/usage` yet drops it from the object it hands the script (verified on
2.1.258 and again on 2.1.266), so the script keeps its own five-minute cache of
the usage endpoint at `~/.cache/claude-usage.json`, filled by a background
refresher and read by the same `jq` that renders. The script re-runs on every
render, so it is held to the same latency budget as `.zshrc`: one `jq` on the
hot path and nothing else, ~20ms measured with the cache read; the refresher
never runs in the foreground. `padding: 0` puts it flush left against the
prompt box rather than indented by one column.

That refresher only ever fires from inside a render, so a machine with no
Claude Code session open just lets the cache age past its one-hour cutoff —
the next session's first render then shows nothing for that row until its own
background fetch lands. `launchd/claude-usage-refresh.plist`, loaded
by `install.sh`, closes that gap by calling `statusline.sh --refresh` every 5
minutes regardless of whether a session is open — see the "THE REFRESHER"
comment in the script for the full split between the two paths.

The portable file also carries `"attribution": { "commit": "", "pr": "" }`,
which is what actually strips the `Co-Authored-By` trailer Claude Code would
otherwise append to every commit. It's in the portable file because in the
untracked `settings.json` alone a new machine goes back to adding trailers.
`.claude/CLAUDE.md` also states the rule, because Codex reads that file and
never reads Claude's settings.

The output and compaction defaults live in `.claude/settings.portable.json`
and merge during installation.

`DISABLE_AUTOUPDATER=1` in the same `env` block keeps Claude Code from replacing
a binary that tweakcc patched. A native install re-checks the retained binary
against Anthropic's signed checksum and swaps in the stock build when it
differs, and `autoUpdates: false` in `~/.claude.json` is ignored on a native
install, so the environment variable is the only switch that works (tweakcc's
README, "Keep customizations across Claude Code updates"). Update by hand with
`claude update`, then re-run `tweakcc --apply --yes`. tweakcc 4.4.0 gets
killed at about 12 GB on Claude Code 2.1.310, and the fix (tweakcc #1053)
is on `main` but unreleased, so `install_tweakcc()` (the `claude` section)
builds the commit pinned in `TWEAKCC_COMMIT` into `~/.local/share/tweakcc` and
links `~/.local/bin/tweakcc` to it. It installs the tool and does not apply it:
`claude update` and `tweakcc --apply --yes` stay manual. When a release newer
than 4.4.0 ships, drop the pin and install from npm. A checkout made by hand in
`~/Developer/tweakcc` is not used by the installer.

`.config/tweakcc/config.json` is the one file of tweakcc's state that is
tracked, and `link_dotfiles()` links it file by file instead of through the
`.config/*` loop. The rest of `~/.config/tweakcc` (the ~270 MB
`native-binary.backup`, `system-prompts/`, `prompt-data-cache/`, the hash files
and `applied.json`) is generated per machine and must not reach the repo.
Linking the directory would move all of it into the repo, or on an
existing machine into a `.backup-*` copy that tweakcc then downloads again.
tweakcc rewrites `config.json` in place on every apply, which follows the link,
so `ccVersion`, `changesApplied` and `lastModified` change in the tracked file
each time. Those three fields are the only per-machine churn; the file holds no
paths or names.

`.config/superfile` is linked the same way, for a different reason. superfile
v1.6.0 compares `~/.local/share/superfile/themeFileVersion` with its own
version and, when they differ, writes every stock theme into
`~/.config/superfile/theme` (`LoadAllDefaultConfig` in
`src/internal/common/load_config.go`). With the directory linked, the first
upgrade would put 21 untracked theme files in the repo. Only `config.toml` and
`theme/voltage.toml` are tracked. superfile overwrites only the stock theme
names, so `voltage.toml` survives an upgrade. `hotkeys.toml` is left as
superfile's default and isn't linked.

Permission rules below remain a manual step. The deny list stops the Read tool
opening files that are only ever noise. `composer.lock` is left readable on
purpose, because working out an installed package version sometimes needs it.
`vendor/` is denied, so in a PHP repo where Claude has to read a library's
source, allow it in that project's own settings rather than here.

```json
"permissions": { "defaultMode": "auto", "deny": [
  "Read(**/*.map)", "Read(**/*.min.css)", "Read(**/*.min.js)",
  "Read(**/dist/**)", "Read(**/node_modules/**)", "Read(**/vendor/**)",
  "Read(**/package-lock.json)", "Read(**/pnpm-lock.yaml)", "Read(**/yarn.lock)"
] }
```

The last two bound what one command, connector call or file read can return.
`bashOutputMaxChars` is a top-level setting, not an env var: Bash output past it
is saved to a file and Claude gets a preview plus the path (default 30000, per
2.1.309's own schema text), so lowering it loses nothing that cannot be fetched.
`BASH_MAX_OUTPUT_LENGTH` looks like the knob for this and isn't; on its own it
only sizes the read-back window. `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` compacts
earlier, because every turn resends the whole conversation; the cost is a
summary that drops detail. It is 15 because the percentage is of a 1M window.
In 14 days of transcripts, 20 of 21 auto-compactions on
`claude-opus-5-5` fired at 146.9k-149.9k `preTokens`, so the 1M assumption
holds even though `settings.json` names plain `opus`. On a model with a 200k
window, 15 would mean ~30k, below the ~57k a session starts with; check
`preTokens` in a `compact_boundary` entry before keeping 15 on such a model. At 70 compaction waited until ~700k tokens, and
a week's transcripts showed a third of all main-session spend on calls
carrying 200k-700k of context. 30 wasn't low enough either: a 7-day audit
found Fable's 44.4M weekly tokens spread over only 196 calls, 77% of them
carrying 200k-400k, mostly sessions switched from Opus to Fable mid-way and
left to run near the 300k line. 15 compacts at ~150k. The env caps live in
`settings.json` and not `.zshenv` because the desktop app does not start
through zsh.

```json
"bashOutputMaxChars": 15000,
"env": {
  "MAX_MCP_OUTPUT_TOKENS": "15000",
  "CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS": "15000",
  "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "15"
}
```

`skillOverrides` trims the skill listing that rides in every system prompt.
The built-in, plugin and claude.ai-synced skills were about 14-15k characters
of descriptions (~3.5-4k tokens, estimated from the listing itself,
not measured with `/context`). 2.1.310's schema text gives four states: `on`,
`name-only` (listed without its description), `user-invocable-only` (hidden
from the model, `/name` still works) and `off`. The lookup takes the full
`plugin:skill` name or the bare one. It works on bundled and claude.ai-synced
skills, but not on the frontend-design plugin's skill: a headless `/context`
still lists it at ~80 tokens under both
`frontend-design:frontend-design` and `frontend-design`, so neither entry is
kept; disable the plugin itself to drop it. That run measured the whole
listing at 968 tokens, with every `name-only` skill under 20. Office files, claude.ai docs, memory import and the writing-style
builder are `off` because nothing here uses them. The rest are `name-only`
rather than `user-invocable-only` so the model can still load them; the
Artifact tool and the Chrome and computer-use MCP instructions already name
the skill to load, so the missing description costs little there. The one real
loss is `claude-api`: its long trigger list is what stops the model answering
model or pricing questions from memory, so set it back to `on` if that starts
happening. `disableBundledSkills` was rejected because it also strips
`code-review`, `simplify` and `loop`. The machine's own toggles for the
`.claude/skills` set stay in the live file; `merge_claude_settings()` merges
this key entry by entry, as it does `env`, so neither list overwrites the
other.

miro, code-simplifier and code-review are disabled for the same reason: miro's
skills and MCP tools cost ~290 tokens and work code can't go to Miro anyway,
and the other two duplicate the built-in `/simplify` and `/code-review`.
Removing them from `CLAUDE_PLUGINS` stops new installs; `enabledPlugins` in the
portable file turns them off where they're already installed, and merges entry
by entry so other plugins stay on. Re-enable one with `/plugin`. Don't judge
this with headless `/context`: with miro off, `claude -p` has no MCP server
and loads ~300 tokens of tool text it otherwise defers.

Claude in Chrome is off by default (`claudeInChromeDefaultEnabled` in
`~/.claude.json`, set by `install.sh`) because its guidance adds ~1.3k tokens
to every session. Use `claude --chrome` when a session needs it. The
computer-use guidance (~700 tokens) has no setting to turn it off.

i-have-adhd is always on: its SessionStart hook injects the ruleset (~1.8k
tokens) whenever `~/.claude/.i-have-adhd-always` exists, which `install.sh`
creates. Delete the file to go back to `/i-have-adhd` per session.

### Editors

Two Neovim configs, deliberately independent: `.config/nvim` (hand-rolled,
lazy.nvim) and `.config/lvim` (LunarVim). They share only `.config/voltage.nvim`,
the colorscheme, which both put on their runtimepath. Never fold one into the
other or copy the palette into either.

### Portable app settings

`merge_claude_settings()` merges `.claude/settings.portable.json` into
`${CLAUDE_CONFIG_DIR:-$HOME/.claude}/settings.json`, preserving other env,
`skillOverrides` and `enabledPlugins` keys, hooks, permissions and plugin state. `merge_codex_settings()` merges
`.codex/settings.toml` into `${CODEX_HOME:-$HOME/.codex}/config.toml`.
Both are called by `link_dotfiles()`. Neither live config is
symlinked or tracked. Re-running a merge with matching values does not rewrite
it. Python 3.11+ is required for the Codex TOML merge; Claude uses Python's JSON
library. Validate source and destination before writing and warn on failure.

## zsh/os

Settings that only make sense on macOS (the Homebrew environment, FlyEnv, the
Xcode toolchain, the LaunchServices and `pmset` aliases, Homebrew's
command-not-found handler) live in `zsh/os/macos-{env,interactive}.zsh` rather
than in `.zprofile` and `.zshrc`. A setting that only names a tool and lets
`$PATH` find it, like `.gitconfig`'s `editor = nvim`, stays in the shared file.

Both source points are load-bearing, and the comments at each say so.
`.zprofile` sources `macos-env.zsh` **last**, because it prepends FlyEnv to
`$path` and has to stay ahead of the array and the overrides block. `.zshrc`
sources `macos-interactive.zsh` after `aliases.zsh` and at the end of the
tool-integration block, so its `command_not_found_handler` is the last one
defined.

## Hosts blocklist

`setup/hosts.sh` filters the StevenBlack list to `0.0.0.0` entries and keeps
`raw.githubusercontent.com` out of the block, so the scheduled updater can
fetch its next copy. `setup/check-hosts-filter.sh` covers both that exception
and filtering multiple hostnames on one input line. The fzf cache filter in
`zsh/extra/cache.zsh` omits the unassignable `zle` option from upstream's
restore expressions; `setup/check-zsh-cache-filters.sh` covers the rewrite and
stale-cache regeneration and cache-write fallback.

## Do not run `install.sh` to test a change

It asks for sudo, edits `/etc/pam.d/sudo_local`, runs `brew bundle`, and loads
LaunchAgents. Verify narrowly instead:

```sh
bash -n install.sh && bash -n setup/lib.sh       # bash: parse both
shellcheck install.sh setup/*.sh \
  .claude/hooks/*.sh .claude/statusline.sh        # ...then lint every one
for f in .zshenv .zprofile .zshrc zsh/*.zsh zsh/extra/*.zsh zsh/os/*.zsh; do
  zsh -n "$f" || echo "FAIL $f"                          # zsh: parse only
done
zsh -ic exit                                  # full interactive load
time zsh -i -c exit                           # startup cost — it is budgeted
stylua --check .config/nvim .config/lvim .config/voltage.nvim
plutil -lint launchd/*.plist                  # plist syntax, no launchctl load
setup/check-claude-settings.sh                # settings merge + command guard
setup/check-hosts-filter.sh                   # blocklist allowlist and multi-host filtering
setup/check-zsh-cache-filters.sh              # fzf option restore + write fallback
setup/check-update-function.sh                # `update` step order, skips and failure report
```

Both file lists are load-bearing. `shellcheck` never sees `setup/*.sh` on its own — those are invoked by
variable name from the `SETUP_SCRIPTS` loop, which it cannot resolve statically,
so they have to be named on the command line. The two scripts under `.claude/`
have no caller in this repo at all — Claude Code runs them from `$HOME` — so
they are named for the same reason. And `zsh -n` parses exactly *one* file:
extra arguments become positional parameters and are silently never read
(`zsh -n .zshenv /nonexistent` exits 0), which is why this is a loop and not a
list. It has to be, because `.zshrc` `source`s `zsh/extra/cache.zsh`,
`zinit.zsh`, `functions.zsh`, `aliases.zsh` and six more `extra/` snippets at
*runtime* — a syntax error in any of them sails past `zsh -n .zshrc` and only
surfaces in `zsh -ic exit`.

`shellcheck` currently exits 1 on a clean tree: three SC2015 `info`s on the
deliberate `cmd && success || warning` lines, two in `install.sh` (the `brew update && brew upgrade` line and the legacy
`pam_tid` cleanup), one in `setup/lib.sh`. All are best-effort steps where the
"C may run when A is true" caveat is acceptable. Read the findings, don't chase
the exit status, and don't rewrite those lines into `if`/`else` just to silence
it.

No line numbers here on purpose: adding a section to an installer shifts
every line below it. Counts and filenames survive an edit; line numbers do not.
Re-derive the list from the command above rather than trusting anything here,
because a stale tally reads as a checksum and invites you to wave through a
genuine new finding as one of the known ones.

Startup latency is a first-class constraint here: plugins are turbo-deferred in
`zsh/zinit.zsh`, tool `init` output is cached via the `zcache` helper defined
near the top of `.zshrc`, and the file byte-compiles itself at the end. Anything
you add to the critical path should be measured, and a new `eval "$(tool init
zsh)"` should go through `zcache`, not straight into `.zshrc`.

## Agent instructions

The repo's own instructions live in `AGENTS.md`, and `CLAUDE.md` is a relative
symlink to it. Codex and Claude Code each find the file under the name they look
for, and there is only one copy of the text to drift.

What each tool does, measured with sentinel files and
`claude -p --tools ""` on Claude Code 2.1.310:

- Claude Code loads `CLAUDE.md` and follows the link. The text loads once.
- 2.1.310 also ships a builtin plugin, `cc-plugin-agents-md`, that loads
  `AGENTS.md`, but only where the project and its ancestors have no `CLAUDE.md`.
  Its `instructionFiles` option (`claude plugin configure
  cc-plugin-agents-md@builtin`) can load it beside `CLAUDE.md` instead. Set
  that way, this repo's rules would load twice.
- Codex reads one file per directory, `AGENTS.override.md` then `AGENTS.md` then
  the `project_doc_fallback_filenames` names, per its docs. It takes `AGENTS.md`
  here and never reaches the link.

Why a symlink and not the other two ways to do this:

- An `@AGENTS.md` import in a real `CLAUDE.md`: deleting that one line drops
  the rules without an error.
- `AGENTS.md` alone, leaning on the builtin plugin, works on 2.1.310 with the
  plugin's defaults. It breaks on an older build, and it breaks if the plugin is disabled or reconfigured. Both fail
  silently.

The link's weak spot is anything that replaces the file rather than writing
into it. GNU `sed -i` turned it into a regular file holding a copy in the same
test, and git shows that only as `typechange: CLAUDE.md`. Claude Code's Edit
tool refuses to write through a symlink and names the target, so Claude itself
is safe. `setup/check-agents-md.sh` checks the link is there and relative, and
that `AGENTS.md` is under 32 KiB, Codex's default `project_doc_max_bytes`. With
`--eval` it also asks Claude Code (haiku, paid) a question only `AGENTS.md`
answers, and runs `codex debug prompt-input` when Codex is installed. The Codex
half hasn't been run yet; Codex wasn't installed on the machine that wrote it.

`~/.codex/config.toml` needs no discovery key for this repo.
`project_doc_fallback_filenames = ["CLAUDE.md"]` is worth keeping for
projects that only have a `CLAUDE.md`, and `project_doc_max_bytes = 65536` is
headroom for project files over the 32 KiB default, which Codex cuts off at
the limit with no warning (measured with `codex debug prompt-input` on
codex-cli 0.164). Both lines go at the top of `config.toml`, above its first
`[table]`; below one, TOML scopes them to that table and Codex never sees them.
The file is untracked because Codex writes it, so the lines are a manual step
on a new machine.

## Generated vs. tracked

This lives here and not in `AGENTS.md` because it only matters when staging.

Do not commit: `*.zwc` (byte-compiled zsh, machine-specific),
`.config/fsh/secondary_theme.zsh`, `.zsh_history`.

`.claude/settings.local.json` is also uncommittable here, but not via `.gitignore`
— the exclude lives in `.config/git/ignore` as `**/.claude/settings.local.json`,
which this repo deploys and is therefore subject to. So `git status` is clean with
that file sitting untracked in the tree; `git check-ignore -v <path>` is what tells
you which rule caught something.

Do commit, even though a tool generates them: `.config/fsh/current_theme.zsh`
(built from our `voltage.ini`; it's what themes a fresh machine) and both
`lazy-lock.json` files (they pin the plugin sets for `:Lazy restore`).

## Critic per work type

This lives here and not in `AGENTS.md` because only a critic pass needs it.
Small tasks get no critic, medium tasks one cold pass, large tasks the full
loop ("Task sizing" in `AGENTS.md`). The pattern is constant; the weapon
changes:

- **Copy/parity:** real reference, blind side-by-side, visual and behavioral.
- **New feature:** rubric plus best-in-class analog; critic uses it cold like a first-time user.
- **Bug fix:** the reference is the repro. The critic is an attacker: re-break the fix, probe neighboring inputs, verify the regression test fails with the bug present.
- **Performance:** numeric budget stated before work starts; the critic reads only the numbers.
- **Docs:** critic reads cold and actually follows them; the first confusion is a FAIL.
- **Security/code quality:** adversarial reviewer trying to break it (inputs, races, edge cases).

## Never hard-code a name

`AGENTS.md` keeps the rule; the recipes live here. A literal user, home
directory or hostname works on the machine it was written on and breaks
without warning on the next one, the same silent failure the installer loops
exist to prevent. Use whatever dynamic form the file format supports:

- Shell: `$HOME`, `$USER` / `$(id -un)`, `$(hostname -s)`, and `~` wherever
  the shell expands it.
- A plist, TOML or YAML with no variables of its own: generate it or
  substitute into it from the installer at deploy time, which is how the
  hosts-refresh LaunchDaemon is built. If the tool reads a path relative to
  `$HOME` or `$XDG_CONFIG_HOME` by itself, drop the path and let it.
- Identifiers such as launchd labels come from a variable derived at install
  time. Don't embed a personal domain or handle.

The identity exceptions (`.gitconfig`'s `[user]` block, `allowed_signers`,
`LICENSE.MD`) exist because Git and SSH read those as literals and can't work
them out.

## Tools that rewrite tracked files

The long form of the offenders list in `AGENTS.md`. `abbr`'s own header in
`zsh/abbreviations` says it drops every comment, so hand edits are how the
section breaks survive; `abbr` is for throwaway experiments. `brew` calls
`git config --global --add` each time a tap trips dubious-ownership, so the
`[safe]` block regrows a copy at a time and shows up as an unexplained diff.
The symlink list itself lives only in the global `.claude/CLAUDE.md`, because
both agents load that file in every project and a second copy would cost
tokens and drift.
